# Fixed-target world model provenance

This record covers the initial PHP `world` package for Minecraft Windows 10 Edition Beta / MCPE 0.15.10.

## Supplied binary/resource evidence

The inspected artifacts are the same fixed-target files recorded for protocol 84:

- `Minecraft.Win10.DX11.exe` — SHA-256 `d5683d2362c62e76dc9e49f8ad08e1462b6f4a8120fca981eb22955368ed38ab`
- `assets-win10.zip` — SHA-256 `25c045e00d8e7f6ffa88592d44dc02c687630c1bf7355bfcbb8c9fd2e1956e6b`
- `assets.rar` — SHA-256 `b5d2038ca2484f76f8d751b48b126cafcc0865f4053bf44006fb3e16e0589509`

The executable exposes fixed-target vocabulary for `Level`, `BlockSource`, `ChunkSource`, `MainChunkSource`, `PlayerChunkSource`, `NetworkChunkSource`, `EmptyChunkSource`, `WorldLimitChunkSource`, `Dimension`, `NormalDimension`, `HellDimension`, `BiomeSource`, `FixedBiomeSource`, and references to `LevelChunk`. It also contains `generator.old`, `generator.infinite`, `generator.flat`, `worldGeneratorType`, and `game_flatworldlayers`.

The shipped English pocket localization independently labels the three fixed-target world types as Old, Infinite, and Flat.

Class/vocabulary strings establish names and ownership seams only. They are not treated as field-layout evidence.

For Overworld biome selection, the executable additionally exposes the concrete layered generator family used by the target: `IslandLayer`, `FuzzyZoomLayer`, `ZoomLayer`, `AddIslandLayer`, `RemoveTooMuchOceanLayer`, `AddSnowLayer`, `AddEdgeLayer`, `AddMushroomIslandLayer`, `AddDeepOceanLayer`, `BiomeInitLayer`, `BiomeEdgeLayer`, `RegionHillsLayer`, `RareBiomeSpotLayer`, `RiverInitLayer`, `RiverLayer`, `SmoothLayer`, `ShoreLayer`, `RiverMixerLayer`, and the Voronoi zoom stage. Recovered constructor flow/seeds match the classic 1.8-era graph (`1`, `2000`, `2001`, `2`, `50`, `70`, `100`, `200`, `1000+`, etc.), including the legacy Hills auxiliary branch whose two zoom layers retain zero-initialized layer RNG state while sharing the normally seeded river-init parent.

The target world-creation seed box resolves through `LevelSettings::parseSeedString`. Inputs shorter than two bytes fall back to a caller-supplied random 32-bit `RandomSeed`; otherwise the box trims only ASCII space/tab/newline/carriage-return, attempts `sscanf("%d")`, specially accepts exact `-1`, and hashes non-numeric/failed `-1` inputs with the target `hash = hash * 31 + signedByte` UTF-8 byte loop. Numeric prefixes are therefore observable (`123abc` resolves to 123), while exact text `Cobblestone` resolves to raw bits `0x6e1def40` / signed `1847455552`. Cobblestone's production launcher mirrors these fixed-target seed-box semantics before passing the same raw 32-bit pattern through its signed PHP/native seed API; exact numeric overflow outside signed 32-bit is rejected because the target C runtime behavior is not portable.

Infinite spawn placement keeps `BiomeSource::getSpawnPosition` as the deterministic X/Z search and the target's Y=128 `LEVEL_SPAWN_HEIGHT` sentinel as a distinct shared-spawn concept. The user's real 0.15.10 offline `mamaMOOSE` save stores raw seed bits `2909061335` (signed `-1385905961`) and shared spawn `4:128:4`. Direct 0.15.10 `Player::recheckSpawnPosition` disassembly shows that first-player placement preserves that X/Z and resolves only Y with `BlockSource::getTopSolidBlock(x,z,true,true)`; unlike the later restored 1.0 source, this target does not run the cardinal `fixStartSpawnPosition` fallback on first entry. Cobblestone's current world/session API intentionally exposes the resolved initial-player surface position (`4:63:4` for this oracle) while respawn/shared-spawn sentinel semantics remain outside this issue. Persistent Infinite metadata stores that resolved session spawn once; legacy provisional metadata is migrated from the authoritative stored seed and generated chunks before StartGame.

For Infinite Overworld terrain shape, the same executable exposes `RandomLevelSource` and its `prepareHeights`/density path. Direct binary inspection pins a 5×17×5 density lattice interpolated as 4×8×4 cells into a 16×128×16 chunk; the raw pre-Voronoi biome plane is sampled at quarter scale with a 10×10 neighborhood. The constructor seeds a 624-word Mersenne-Twister state directly from the target's 32-bit `RandomSeed` (not Java's 48-bit `Random`) and constructs noise banks in the fixed order: 16-octave min limit, 16-octave max limit, 8-octave main, 4-octave surface simplex, 10-octave scale, 16-octave depth, 8-octave forest. Surface/scale/forest are not all read by `prepareHeights`, but their constructors consume the shared RNG stream and therefore remain generation-significant.

The executable also exposes the distinct `RandomLevelSource::buildSurfaces` stage and biome virtual surface overrides. Binary RTTI/vtable/disassembly identifies the base `Biome::buildSurfaceAt` plus specialized target overrides for `ExtremeHillsBiome`, `MesaBiome`, `MutatedBiome`, `MutatedSavannaBiome`, `SwampBiome`, and `TaigaBiome`. The stage reseeds its per-chunk MT stream with wrapping `chunkX * 341872712 + chunkZ * 132899541`, samples the retained four-octave surface simplex at 1/8 block scale, places 2..5 bottom bedrock layers per column, and then applies biome top/filler rules. Mesa/Bryce additionally owns world-seeded clay-band, pillar, and roof simplex noise; generic mutated biomes delegate surface behavior to their contained parent.

For Overworld carving, the same 0.15.10 executable exposes `LargeCaveFeature` and `LargeHellCaveFeature`; no separate Overworld ravine/canyon generator RTTI/vocabulary is present, and the recovered `RandomLevelSource` load path applies `LargeCaveFeature` immediately after surfaces. The matching restored MCPE source at `theaperturecat/MCPE-1.0.0-Restored@c095fbd72bbd88d25e6a550c86cbcc659924c4e6` reconstructs the target mechanism: world-seed-derived odd X/Z scales, an inclusive radius-8 source-chunk scan, per-source MT reseeding, nested cave-count gating, room/tunnel recursion, float trigonometric drift with `nextGaussianFloat() == nextFloat() - nextFloat()`, water-boundary abort/flowing-water conversion, Y<10 still-lava replacement, the exact diggable block set, thin-sand sandstone/red-sandstone repair, and exposed-grass repair. Block IDs and metadata are separate in the target, so carve replacement changes the ID byte without clearing its metadata nibble.

For post-carving population, the target executable exposes RTTI for `LakeFeature`, `BiomeDecorator`, `MesaBiome::Decorator`, and `OreFeature`. The pinned restored source shows that `RandomLevelSource::postProcess` owns a 3x3 chunk neighborhood. Infinite/Overworld constructs `RandomLevelSource(..., false)`, so the misleadingly named `legacyDevice` branch is disabled for this generator: underground water attempts are not suppressed and lava-lake attempts are enabled. Water lakes are excluded only for Desert/DesertHills, take a 1/4 gate, choose X/Z in [3,12) and Y in [0,128), and set `hasLake` even when `LakeFeature::place` aborts. If no water attempt claimed the slot, lava takes a 1/8 gate, uses nested Y sampling, then only places for Y>=60 with Y60..63 unconditional and higher Y requiring another 1/10 gate.

`LakeFeature` descends through air, offsets the cavity by (-8,-4,-8), unions 4..7 random ellipsoids into a 16x8x16 mask, aborts when upper boundary cells touch liquid or lower boundary cells are non-solid/nonmatching liquid, fills the lower half with still water/lava and upper half with air, and for lava probabilistically converts solid boundary cells to stone. Its dirt-to-grass repair checks current skylight >0; generated Overworld chunks have default `Brightness::MIN` skylight before the later post-process light update, so that repair is inert at this stage. Out-of-height block reads resolve to air.

For Village structures, the executable independently exposes `StructureFeature`, `StructureStart`, `StructurePiece`, `VillageFeature`, `StartPiece`, `StraightRoad`, `SimpleHouse`, `SmallTemple`, `BookHouse`, `SmallHut`, `PigHouse`, `DoubleFarmland`, `Farmland`, `Smithy`, `TwoRoomHouse`, and `LightPost`. The shipped `assets-win10.zip` does not contain Village layout/template resources; its Village-related entries are presentation assets such as villager textures and sounds. Structure geometry/RNG therefore comes from executable/restored-source evidence rather than asset templates. The pinned restored source recovers the radius-4 source scan, 40-chunk spacing with 12-chunk minimum separation, salt `10387312`, the target's negative-coordinate pre-adjustment/C++ division behavior, raw-biome gate (Plains, Desert, Savanna, Ice Flats), 1/50 abandoned gate, piece weights/counts, road/house expansion order, biome style substitutions, terrain-height alignment, and chunk-clipped piece post-processing. The restored 1.0 branch comments out `StraightRoad::postProcess` path writes, but this is not 0.15.10 behavior: the actual `Minecraft_PE_0.15.10.apk` ARM `libminecraftpe.so` (`SHA-256 f1114861cfe000d4c7698c2c877db32c7eb9ad2404341ec4e14993524431bc44`) exports an active `StraightRoad::postProcess` at RVA `0xd6f748`. Its X/Z scan checks the chunk box at Y=64, calls `getTopSolidBlock`, selects `Block::mGrassPathBlock` or `Block::mWoodPlanks` when the top material is liquid, and calls `setBlockAndData`; Cobblestone mirrors that target behavior. The later restored source's commented `createDoor`/`createChest` placement bodies remain separate no-op evidence.

Village starts are historyful rather than reconstructible from one chunk in isolation. The target caches starts, lets each center chunk post-process only intersecting pieces, records generated chunk hashes transiently for idempotence, and does not serialize that generated-chunk bookkeeping. Cobblestone mirrors the model with reusable native `StructureStartCore` + `StructureStartCache<T>` machinery and family-specific `VillageStructureState`; reload preserves durable start/piece state while intentionally resetting generated-chunk bookkeeping.

Mineshafts are the next fixed-target structure family. The executable exposes `MineshaftFeature`, `MineshaftStart`, `MineshaftRoom`, `MineshaftCorridor`, `MineshaftCrossing`, `MineshaftStairs`, and `MineshaftPiece`; the shipped archive contains no Mineshaft layout/template assets. The recovered feature uses the generic radius-8 `LargeFeature` source scan, discards one random integer in `StructureFeature::addFeature`, then accepts a source only when `nextFloat() < 0.004` and `nextInt(80) < max(abs(chunkX), abs(chunkZ))`. Mesa-family sources are detected from the final biome at the source chunk's northwest block and use dark-oak metadata, a 0.5 room expansion chance, and a sea-level-biased vertical move; ordinary Mineshafts use oak, room chance 1.0, and `moveToLevel(seaLevel - 10)`. The four procedural piece families preserve target recursion/collision/depth limits, liquid-edge abort/removal, chunk clipping, support/web/rail RNG, generic spider-spawner block placement, and transient generated-chunk bookkeeping. In this restored branch `StructurePiece::getBrightness()` returns default zero, and the `LevelChunk` call that would invoke `postProcessMobsAt()` is commented out, so dormant minecart-chest entity population is not fabricated by Cobblestone.

Strongholds are likewise procedural; the executable exposes the Stronghold feature/start plus Straight, PrisonHall, Left/RightTurn, RoomCrossing, StraightStairsDown, StairsDown, FiveCrossing, ChestCorridor, Library, PortalRoom, and FillerCorridor piece families, while the shipped archive contains no Stronghold structure templates. Fixed-target PE placement is not the modern Java ring algorithm: the first three positions are found by scanning around an angle/distance sequence for full valid Village feature chunks, then additional Strongholds use 200×200-chunk grid cells with a 150-chunk inset, minimum origin distance 10, and 25% per-grid chance. Piece generation preserves the target's copied-`Random` selection bug, finite weight exhaustion, forced first FiveCrossing, collision-driven filler fallback, random pending-child order, and `moveToLevel(seaLevel - 5)`. All 12 piece families use the target smooth-stone selector and chunk-clipped post-processing; Stronghold chest creation is commented out in this branch, while PortalRoom places a generic mob-spawner block but its silverfish entity assignment is commented out. Portal frames roll twelve independent `nextFloat() > 0.9` eyes and only the all-eyes branch places the 3×3 End Portal.

For scattered Overworld structures, the 0.15.10 executable exposes `RandomScatteredLargeFeature`, `ScatteredFeaturePiece`, `DesertPyramidPiece`, `JunglePyramidPiece`, and `SwamplandHut`; it does not expose `Igloo`. The matching restored 1.0 source is therefore ahead of this target where it also contains Igloo support. Independent historical Bedrock asset reports place the first `structures/igloo/*.nbt` addition at 0.17.0.1 / the 1.0.0 beta, so Cobblestone deliberately keeps Igloo out of the 0.15.10 family. The fixed-target scattered locator uses the generic radius-8 source scan, one `StructureFeature` clear draw, spacing 32 with minimum separation 8 and the target negative-coordinate pre-adjustment, then a raw chunk-center biome gate: Desert/Desert Hills select Desert Pyramid, Jungle/Jungle Hills select Jungle Pyramid, and Swampland/Swampland Mutated select Swampland Hut. The three target pieces are procedural; `assets-win10.zip` contains no scattered-structure templates.

Scattered piece orientation is hard-coded South in this target. Jungle/Hut ground alignment is historyful: the first intersecting chunk averages only the piece columns inside that chunk using `aboveTopSolidBlock(..., includeWater=true)`, persists that height, and moves the piece by the recovered offset. Desert Pyramid stays at Y=64. The target `createChest()` body is commented out, so Desert and Jungle chest flags never become true; Jungle `createDispenser()` still places the two trap dispenser blocks and persists those flags, while dispenser loot filling is commented out. Hut cauldron contents and witch spawning are likewise commented/dormant in the ordinary chunk path. Jungle preserves the recovered broken directional behavior where the generic piston/lever/dispenser rotation branch is commented out; only the active block-specific orientation transforms apply.

Ocean Monument generation is deliberately absent from the 0.15.10 parity surface. The target executable contains no `OceanMonumentFeature`, Guardian/Elder Guardian, Prismarine, or Sea Lantern runtime vocabulary, and shipped vanilla `blocks.json` does not register Prismarine or Sea Lantern block identities. Some themed resource packs already contain future Guardian/Prismarine imagery, but those files are not live registry/world-generation evidence. Mojang's own MCPE/Win10 0.16 release notes list Ocean Monuments, Guardians/Elder Guardians, Prismarine variants, and Sea Lantern as new 0.16 features. The restored 1.0 source's `OceanMonumentFeature`/`OceanMonumentPieces` implementation is therefore post-target reference code and must not be ported into the 0.15.10 generator.

Monster Rooms run immediately after the target structure post-process sequence on that same population MT stream. Direct inspection of the uploaded 0.15.10 executable exposes `MonsterRoomFeature` plus the generic MobSpawner runtime family. The pinned restored source recovers eight attempts per center chunk, with X/Z selected as `chunkOrigin + nextInt(16) + 8` (therefore 8..23 and intentionally able to originate in the east/south neighbor), Y in 0..127, and independent X/Z radii of 2..3. A room is accepted only when the complete floor and ceiling material planes are solid and its side boundary exposes 1..5 two-block air openings. Placement preserves the target's cobblestone walls, 3/4 mossy floor selector, cavity carving, two chest attempts with exact facing metadata, and generic mob-spawner block. The restored branch has both simple-dungeon chest loot filling and the spawner entity-id assignment commented out, so Cobblestone places neither loot payload nor mob target and does not consume the dormant spawner `nextInt(4)` draw. The supplied Win10 assets contain chest/spawner presentation resources but no `simple_dungeon` loot-table or Monster Room structure template, so geometry and RNG provenance come from executable/restored-source evidence rather than assets.

The following `freezeFrostProcess` is one place where the restored 1.0 source is materially misleading for the 0.15.10 target: that source comments out the body of `BlockSource::shouldFreeze`, but direct disassembly of the uploaded 0.15.10 Win10 executable shows the logic active inline. It scans exactly the center chunk's 16×16 columns with no RNG, resolves `getTopRainBlockPos`, tests the column biome's fixed PE temperature against `0.15f`, requires Y in 0..127 and block light below 10, then freezes data-0 flowing or still water to legacy ice ID 79. The generated block-light plane is still zero here; earlier emitters are only deferred until the later light pass, so the light check always passes at this generation boundary. PE also does not apply Java's altitude temperature adjustment, leaving exactly Frozen Ocean, Frozen River, Ice Plains, Ice Mountains, Cold Beach, Cold Taiga, Cold Taiga Hills, Ice Plains M, and Cold Taiga M at or below the threshold. The target rain-height helper itself starts at Y=127, never examines Y=0, treats either motion-blocking material or liquid as a rain blocker, and caps a discovered Y+1 back to 127, so a blocker at Y=127 makes the freeze candidate Y=126. Despite the profile name, this pass contains no top-snow placement; shipped ice/snow assets establish registry/presentation support only, while snow accumulation belongs to the later Seasons/weather path.

The same post-process later reseeds the MT stream immediately before `biome.decorate`, making common ore RNG independent from earlier lake/structure/dungeon/freeze RNG consumption while still observing whatever blocks those earlier stages changed. `BiomeDecorator::decorateOres` places dirt/gravel, the PE-specific 1/16 eighty-vein extra-gravel burst, diorite/granite/andesite, coal/iron/gold/redstone/diamond/lapis in fixed order; Mesa decorators then add twenty gold veins from Y=32..79. `OreFeature` uses target float sin/cos ellipsoids, floor-based `BlockPos` conversion, and replaces only stone/netherrack.

The remainder of `Biome::decorate` stays on that same freshly reseeded MT stream after ores. The recovered common order is sand/clay/gravel disks, tree selection plus PE tall-grass scatter around selected trees, huge mushrooms, flowers, tall grass, dead bushes, water lilies, small/extra mushrooms, configured reeds plus the extra ten reed attempts, pumpkin, cactus, then fifty water and twenty lava spring attempts. The target cached chunk heightmap is captured before population and is not recomputed by earlier lake/structure/dungeon/freeze writes; decorator height queries therefore read that pre-population map. Infinite passes `legacyDevice=false` and `FLT_MAX`, enabling the non-legacy grass/double-plant paths and leaving the decorator's distance-based spring suppression unreachable.

Biome subclasses preserve their target pre/post hooks and quirks: Plains/Sunflower Plains place double plants before common decoration; Roofed Forest lays its 4×4 tree/mushroom grid first; Taiga performs the recovered X/Z-swapped rock/fern attempts; Savanna adds double grass; Ice Plains Spikes adds three ice-spike and two ice-patch attempts; Desert appends its 1/500 well; Extreme Hills appends emerald and monster-egg ore; Jungle appends melon and fifty vine attempts. Generic `MutatedBiome::decorate` deliberately calls the contained biome's decorator directly, skipping the contained subclass's decorate override, while special mutated biome classes that construct a new concrete biome retain their own hooks. Direct inspection of the uploaded 0.15.10 executable exposes RTTI for the implemented decorator/tree feature family (`BiomeDecorator`, sand/clay/flower/grass/reeds/cactus/waterlily/pumpkin/spring/well, oak/birch/spruce/pine/fancy/swamp/jungle/mega/acacia/dark-oak, ice patch/spike, vines/melon and related classes) and does not expose `FossilFeature`; later fossil generation is therefore excluded. Shipped Win10 assets independently contain the matching decoration presentation vocabulary such as double plants, podzol, cactus, reeds, water lilies, acacia, mushrooms, melon, and pumpkin, but are not used as an algorithm oracle.

After biome decoration, Infinite performs the target post-decoration finalizers in strict order. `_fixWaterAlongEdges` scans exactly sixty perimeter columns using the cached generation heightmap, converts only the first still-water block in each vertical still-water run to flowing water, and enqueues that block for a delay-1 generation tick. The same generation-owned queue also receives liquid work triggered by `SpringFeature`'s immediate dynamic-liquid tick during decoration. The target then runs generation-time Seasons/top-snow when the center chunk carries a dirty snow profile, drains every pending generation tick, and finally recomputes the finished center chunk's height, sky-light, and block-light planes.

Generation Seasons is distinct from later runtime weather. It uses the fixed target snow-noise setup seeded with `89328`, the recovered five-octave 3D simplex path, biome snow accumulation/min/max profiles, target rain-height and placement rules, and `TopSnowBlock`'s covered-bit representation. Recoverable tall grass/flowers/mushrooms displaced by top snow are preserved in sparse extra data with low 8 bits = block ID and high 8 bits = data. Generic Cold Taiga M keeps the target mutated-biome quirk of copied accumulation with default min/max snow bounds. Final light/height processing uses the fixed-target block light-block/emission properties over the shared 3x3 population neighborhood, allowing neighboring emitters within the target propagation distance to contribute to the center chunk before its packed nibble planes are persisted.

## Ardosia semantic oracle

Ardosia was inspected at:

- repository: `ardosia/ardosia`
- branch: `main`
- revision: `766f2a2a073889583334758b500b7b6e05acb1f1`

Its fixed-target world model freezes:

- 16×16 horizontal chunks;
- 16×16×16 sections;
- 8 vertical sections;
- world Y range 0..127 (height 128);
- Euclidean chunk mapping for negative block coordinates;
- per-column biome identity;
- separate sky-light and block-light channels;
- immutable/snapshot boundaries above mutable resident terrain.

Cobblestone ports these structural semantics to PHP. It does not port Ardosia's Rust locks, resident-handle graph, game-world leases, or native ownership implementation.

## Matching 0.15.10 source cross-check

The already accepted protocol-84 source oracle was consulted at:

- repository: `KhronosDevs/PocketMine-MP`
- revision: `15272732371b4e7785cc9f45b6274b31198d518e`

Relevant fixed-target facts are:

- the live dimension domain is exactly `0 = Overworld/Normal`, `1 = Nether/Hell`; matching `Level` and `ChangeDimensionPacket` constants expose those IDs, and this 0.15.10 target has no live End dimension;
- StartGame generator ids: `0 = old`, `1 = infinite`, `2 = flat`;
- chunk block coordinates use x/z 0..15 and y 0..127;
- legacy block state is block id 0..255 plus data 0..15;
- extra block data is a separate 16-bit value;
- chunk state carries heightmap, biome id/color, block data, sky light, block light, and generated/populated/light-populated lifecycle flags;
- the historical Flat default preset is `2;7,2x3,2;1;`: bedrock, two dirt layers, grass, biome 1;

The initial Cobblestone package keeps the preset syntax and structural state but intentionally does not import decoration/populator behavior.

An earlier validation pass treated Java 1.8 `cubiomes` output as equivalent to the MCPE graph; the real 0.15.10 client/save disproved that assumption. The real offline `mamaMOOSE` chunk at 0:0 is now the end-to-end biome oracle: its 256 final biome bytes hash to `0xdfba91c444c4dfc3`, containing 239 Plains columns and 17 River columns, and the corrected source also yields the target shared-spawn X/Z `4:4`. Java `MC_1_8` fixtures are no longer treated as parity evidence.

Terrain-shape reconstruction was cross-checked against the near-target restored MCPE source `theaperturecat/MCPE-1.0.0-Restored@c095fbd72bbd88d25e6a550c86cbcc659924c4e6` only where its `RandomLevelSource`, MT `Random`, `PerlinNoise`, `ImprovedNoise`, biome height table, and stage ordering matched facts independently recovered from the 0.15.10 executable. The target binary pins the density constants used here: coordinate/height scale `684.412`, min-limit Y scale `×1.25`, min/max normalization `÷256` / `÷512`, 3×3 biome-height smoothing, base size `8.5`, top-four-lattice slide to `-10`, and Overworld sea fill below Y=63. Focused MT/Perlin/Simplex fixtures remain independent target checks; full pre-surface chunks are composition-regression snapshots under the corrected MCPE biome graph rather than mislabeled Java-biome oracles.

## Cobblestone API decisions

The client-facing C++ `Level` concept maps to ordinary PHP `Cobblestone\World\World`. `BlockSource` and `ChunkSource` remain explicit interfaces because they form useful semantic ownership/access seams. `MainChunkSource` is the owner-runtime resident index backed by the configured generator.

`GeneratorType` retains the three fixed-target ids because they are part of the StartGame/world vocabulary. `FlatGenerator` and `InfiniteGenerator` are complete public Overworld generators today. Infinite composes the exact recovered `BiomeSource`, `prepareHeights`, `buildSurfaces`, `LargeCaveFeature`, 3x3 population boundary, lakes, Village/Mineshaft/Stronghold/Scattered stateful structures, Monster Rooms, freeze/frost, biome decoration, water-edge/Seasons/generation-liquid finalizers, and final light/height output as one coarse native pipeline. Representative whole-pipeline fixtures cover normal, cold/snow, Savanna, and Desert Pyramid chunks; persistent composition stores generator-owned historyful structure state separately from chunk records. Old remains intentionally deferred/unimplemented.

`Dimension` is a separate backed enum with the exact fixed-target IDs `Overworld = 0` and `Nether = 1`. World creation defaults to Overworld, persistent metadata is authoritative on reopen, and StartGame receives the stored world dimension instead of a hard-coded zero. Dimension identity is intentionally implemented before Nether generation/portals so later world semantics have a stable durable domain.

Legacy block state remains represented on hot paths by one scalar `BlockStateId` (`id << 4 | data`). Public semantic identity is the closed backed enum `BlockType`, whose 191 singleton cases carry the exact legacy IDs and exact asset names; `BlockData` is the closed 0..15 metadata nibble; and `BlockState` is immutable `BlockType + BlockData`. Semantic code therefore names blocks instead of passing legacy numeric IDs, while native/chunk/storage/protocol paths keep the compact integer state token. PHP/native public state input rejects IDs outside the 191 asset-backed registry. Native generated-world storage additionally accepts explicitly recovered executable-only states such as End Portal 119, because exact target generation can emit them. Block behavior belongs to a later package and is deliberately not modeled here.

The production server now selects a region-sharded native `WorldStore` whenever the extension is loaded. Rust owns the physical chunk planes, biomes, heightmap, sparse extra data, terrain/light revisions, immutable snapshots, and atomic revision-checked patches; PHP remains authoritative for world/gameplay semantics, chunk residency decisions, generator policy, mutation callbacks, and light-propagation rules. The PHP representation is retained as a parity-tested fallback rather than the production storage target.

Immutable `ChunkSectionSnapshot` / `ChunkSnapshot` projections are the bulk read boundary. Large staged mutations switch to a snapshot after a small number of native point reads, while commit remains one patch per changed chunk. Lighting uses one immutable snapshot per touched chunk, scalar staged light levels, exact terrain/light revision validation, and one patch per changed chunk. Protocol-84 initial streaming reads native snapshots directly inside the extension, caches FullChunkData by terrain/light revision, compresses the Batch, and submits it through the session host. The old synthetic probe remains exported only for ABI compatibility and is no longer on the production join path.

## World API parity expansion

`world-api-parity-v1` uses `ardosia/ardosia@766f2a2a073889583334758b500b7b6e05acb1f1` `crates/world` as the semantic oracle for the broader world substrate.
